static final long spinForTimeoutThreshold = 1000L;
当线程等待锁的剩余时间小于或等于这个阈值时，不进行挂起，而是选择快速自旋等待。
因为挂起LockSupport.parkNanos挂起线程是一个相对“重”的操作，涉及操作系统调度，上下文切换等。如果等待时间极端，比如几百纳秒，挂起再唤醒的开销可能比直接
空转(自旋)还要大。
 牺牲了极短时间内的CPU资源，换取了更高的响应速度和更低的系统开销。这个值1000L是经过大量测试和经验得出的"经验值"，在绝大多数场景下都能取得较好的性能平衡。

 public final boolean hasQueuedPredecessors() {
         // The correctness of this depends on head being initialized
         // before tail and on head.next being accurate if the current
         // thread is first in queue.
         Node t = tail; // Read fields in reverse initialization order
         Node h = head;
         Node s;
         return h != t &&
             ((s = h.next) == null || s.thread != Thread.currentThread());
     }

上面的方法 是否拥有前一个队列元素。换言之：当前线程用不用排队。返回false 不用排队，返回true，需要排队

上面方法中 先读取tail节点给到局部变量t  再读取head节点给到局部变量h 为什么要先读取tail 再读取head 其实是主要防止后面的h.next报空指针，原因是什么呢？
 队列初始化的时候 会执行enq方法里面的一段代码，具体如下
    private Node enq(final Node node) {
            for (;;) {
                Node t = tail;                          --------------1

    初始化队列有上面四句代码，着四句代码不是原子的，可能执行任何一行代码后，cpu让出执行权。我们分场景分析一下

     上卖弄初始化代码是先给head赋值，然后再给tail赋值，那么就知道
        a、如果tail为null，那么head 可能是null 也可能不是null
        b、如果tail不为null，那么head一定不为null
     在hasQueuedPredecessors方法中，如果我们是按照先将head的值赋值给h，再执行tail的值赋值给t的话 可能存在
        a、执行Node h = head 时，同步队列已经初始化完成，也就是上面4行代码都执行完成了，那么此时h和tail都不为null
        b、执行Node h = head 时，上面第三步还未执行，那么此时h就赋值为null了，第三步为执行那么第四步肯定还未执行(volatile屏障机制，不会重排序) 此时h 和 t都是null
        c、执行Node h = head 时 未执行到第三步，那么此时h赋值就是null了，在执行Node t = tail时，上面执行了第四步，那么此时h为null tail 不为null  这种
        情况是有问题的，因为h==null tail!=null h!=t,那么s = h.next时就会报空指针了
        d、执行Node h = head 时 已经执行了第三步，h不为null，然后等到执行Node t = tail时，上面第四步还未执行，此时h!=null tail==null 不会出空指针
     所以先读取head 赋值给h  再读取tail赋值给t 会有c这种情况有问题，所以不能先读取head 再读取tail

     那我们看下先读取tail再读取head

        a 执行Node t = tail 时，上面第三步还未执行 那么t为null 执行Node h = head 时上面第三步还未执行，h也为null
        b 执行Node t = tail 时，上面第三步执行 但是还未执行第四步，执行Node h = head 那么此时t为null h不为null
        c 执行Node t = tail 时，上面第三步执行，第四步也执行完成 执行Node h = head，那么此时h和tail都不为null
     所以先执行Node t = tail 再执行 node h = head 不会产生h为null  t不为null的情况。


    继续分析后面的  ((s = h.next) == null || s.thread != Thread.currentThread());
    要走到上面代码 一定是h!=t
     符合这种情况的：
      a、 h!=t 有两种情况 一种是还未初始化完成h 不为null  t为null 一种是已经有入队的node了
          如果(s = h.next) == null  成立 说明 上面第三步已经完成，但是还没有执行tail=head 也就是第四步还未执行，导致h!=t成立，此时
      h.next == null 也就是(s = h.next) == null成立，这个时候表明已经有线程在执行入队操作了，只是还没有入队完成，那么当前线程需要排队
      就是返回true
      b、同步队列已经完成了初始化，但是由于释放锁等操作，导致此时同步队列中只有一个头节点，head和tail都指向这个头节点，此时有一个线程执行入队操作
      ，刚执行完compareAndSetTail(pred,node)，把tail指针指向自己新建的节点，导致h !=t成立，但是还没有执行pred.next = node; 所以此时
      (s = h.next) == null也成立，说明此时也有线程再入队，但是还没入队完成，那么当前线程也是需要排队。

     还有一种场景h!=t成立，(s = h.next) == null  不成立，就需要s.thread != Thread.currentThread()这个判断 ，说明当前同步队列至少
     有两个节点并且头节点的后继节点不为null，并且说明这个后继节点锁代表的线程跟当前线程不是同一个线程，这个就是最标准的情况了，同步队列中已经有线程
     在等着获取锁了，那么当前的线程就只能取排队了。


    public final void acquire(int arg) {
        if (!tryAcquire(arg) &&
            acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
            selfInterrupt();
    }
    上面的acquire(获得)的方法主要有三个逻辑
        a、尝试获取，主要就是判断state状态
        b、addWaiter 主要就是入队，分为两种情况:未初始化  已初始化
        c、acquireQueued 入队的Node(线程)是否要在尝试获取一次锁，如果是第一个等待的就再尝试一次，剩下的就要挂起，不能一直死循环获取
    因为我们的方法就是获取锁，所以我们的这些代码逻辑中，不是原子操作的，就都会有并发情况。
    获取的锁的本质是什么呢，就是当前线程调用acquire方法后，是否会进入阻塞，拿到锁就不阻塞，拿不到就阻塞。


    final boolean acquireQueued(final Node node, int arg) {
            boolean failed = true;
            try {
                boolean interrupted = false;
                for (;;) {
                    final Node p = node.predecessor(); ------------------------1
                    if (p == head && tryAcquire(arg)) {  ------------------------2
                        setHead(node);       ------------------------3
                        p.next = null; // help GC    ------------------------4
                        failed = false;      ------------------------5
                        return interrupted;    ------------------------6
                    }
                    if (shouldParkAfterFailedAcquire(p, node) &&
                        parkAndCheckInterrupt())   ------------------------7
                        interrupted = true;
                }
            } finally {
                if (failed)                            ---------------------- 8
                    cancelAcquire(node);              ---------------------- 9
            }
        }

----------------------进入到上面的acquireQueued方法后，会不会有并发情况呢 我们一句一句分析
 1代码  因为node是当前线程刚入队的节点，它的前驱节点p在入队完成后是固定的， 同步队列中节点的prev指针在入队时就已经确定，且不会被其他线程修改 所以这一句不存在并发问题
 拿到的p一定是当前节点的真实前驱。

 2代码 因为node刚入队，

      执行tryAcquire时会失败，然后就会走到7代码，判断释放挂起
      如果此时没有线程拿到锁，那么这里的tryAcquire(arg) 会成功，那就成功返回了
      如果此时没有线程拿到锁 还有一种特殊情况，在调用tryAcquire(arg)时成功了，但是在成功之前当前线程被打断了，仍然会拿到锁，但是会返回false，

       if判断是false，不会selfInterrupt 不会走，没有本次这次打断就没有被消费，无需这里的selfInterrupt，所以在当前线程中，还是可以用isInterrupted获取中断标记的。
     如果tryAcquire(arg)没有成功，会走到7代码，调用shouldParkAfterFailedAcquire(p, node) 判断是否应该被挂起
        公平锁中第一个等待节点且tryAcquire(arg)如果没有成功 ，那么就是有不在队列中的一个线程还未释放锁，这边shouldParkAfterFailedAcquire(p, node)中判断p不是signal
        ，然后将p设置为signal，等到持有锁的线程释放锁的，时候，会看到head是signal，然后就会唤醒下一个节点，但是这里，如果在释放锁的时候，head还未被设置为signal，那还有办法
        唤醒吗，这里如果还未设置为signal，说明还未阻塞，这个线程还继续执行，设置为signal，然后返回false，那么 acquireQueued方法的死循环会再次调用，判断2行的代码p==head
        且这次已经释放锁了，能拿到锁了，就不会阻塞了。


      线程的Thread.interrupted() 获取中断标记 + 清除中断位(用完变为false)
           实例.interrupt() 发中断请求，设置线程中断标记为true，不会立刻停止线程
            Thread.isInterrupted()获取当前中断标记，不清除标志

  为什么上面failed是true的时候才调用cancelAcquire?
  只有成功拿到锁 才会把failed设为false，并直接退出循环。

  只有线程在获取锁的过程中被异常终止，且没有成功拿到锁，才会走到finally filed=true  此时 线程已经不可能再继续自旋枪锁了，但它还在AQS队列里，
  如果不清理，会变成僵尸节点，阻塞后面线程的唤醒。
   当成功拿到锁，就不需要cancelAcquire，线程已经成功获取到锁，setHead(node)已经把当前节点变成新的哨兵节点，脱离了等待队列。

   failed = true  线程永远拿不到锁了，要从队列中清理
   failed = false 线程已经拿到锁了，节点已经变成新的哨兵，无需取消，继续参与锁的流程。

private void cancelAcquire(Node node) {
        if (node == null)                  ---------------------------------1
            return;
        node.thread = null;                ---------------------------------2
        Node pred = node.prev;             ---------------------------------3
        while (pred.waitStatus > 0)        ---------------------------------4
            node.prev = pred = pred.prev;   ---------------------------------5
        Node predNext = pred.next;         ---------------------------------6
        node.waitStatus = Node.CANCELLED;   ---------------------------------7
        if (node == tail && compareAndSetTail(node, pred)) {  ---------------------------------8
            compareAndSetNext(pred, predNext, null);      ---------------------------------9
        } else {
            int ws;
            if (pred != head &&
                ((ws = pred.waitStatus) == Node.SIGNAL ||
                 (ws <= 0 && compareAndSetWaitStatus(pred, ws, Node.SIGNAL))) &&
                pred.thread != null) {              ---------------------------------10
                Node next = node.next;
                if (next != null && next.waitStatus <= 0)   ---------------------------------11
                    compareAndSetNext(pred, predNext, next);  ---------------------------------12
            } else {
                unparkSuccessor(node);   ---------------------------------13
            }
            node.next = node; // help GC
        }
    }


1和2 是安全校验，如果为空，什么都不做
3，4，5 是从当前节点开始 判断前一个节点的状态是否为cancel状态，是的话就将当前节点的前一个节点设置为前一个节点的前一个节点。 最终，pred指向
最靠近当前节点的，未被取消的前驱节点。 能保证后续操作基于有效前驱，避免队列中堆积无效取消节点
7 原子性赋值，java的变量赋值是原子操作，将当前节点标记为取消，后续线程会自动跳过它









    private void unparkSuccessor(Node node) {
        int ws = node.waitStatus;
        if (ws < 0)
            compareAndSetWaitStatus(node, ws, 0);
        Node s = node.next;
        if (s == null || s.waitStatus > 0) {
            s = null;
            for (Node t = tail; t != null && t != node; t = t.prev)
                if (t.waitStatus <= 0)
                    s = t;
        }
        if (s != null)
            LockSupport.unpark(s.thread);
    }

第一步将传入的node的状态设置为0，是因为判断了ws<0，小于0的状态有SIGNAL CONDITION PROPAGATE ,SIGNAL PROPAGATE 这两个状态的触发场景不同，
但SIGNAL 用于独占锁的串行唤醒，后者用于共享锁的批量传播唤醒。但他们在unparkSuccessor方法中处理的逻辑是完全一致的。CONDITION状态不会在同步队列
存在。
    compareAndSetWaitStatus(node, ws, 0);这一行的作用是将状态设置为0，使用CAS是为了确保只有当前线程成功将状态从负数改为0，其他线程即使
也尝试修改也会失败，从而避免了多个线程同时唤醒同一个后继节点的问题。
    这里compareAndSetWaitStatus(node, ws, 0) 这一步如果失败 为啥不使用重试(自旋)?这里设置失败意味着其他线程正在并发修改这个节点的状态。能修改
当前节点状态的线程，只有它的后继节点。说明此时后继节点正在执行shouldParkAfterFailedAcquire，并且已经成功把状态改回了-1.

       这里为什么要从尾节点开始向前遍历呢
        入队的时候是先设置前驱指针，再设置后继指针，这两步不是原子的，如果从后往前找，因为入队时是先设置prev指针的，所以只要节点进入了队列，它的prev指针
        一定是有效的，通过tail一路沿着prev往回找，一i的那个能找到那个刚刚入队，但next还没有来得及被赋值的节点。 确保能找到那些"正在排队但还没完全排好"的节点

        为什么状态是小于等于0，而不是只找-1的， 新入队的节点默认状态是0，如果只找-1，会漏掉那些刚进来还没来得及把自己改成-1的线程。
       一直覆盖s的值，是为了找到离head最近的那个有效节点。
